# 2026-10-14 启播与定位性能审计

本轮从已发布 `d6286fc` / `1.1.0-1.58` 继续。测试始于 10 月 13 日，完成于
10 月 14 日；产物与日志保存在工程外 `outputs/playback-performance-20261013/`。
本轮只修改本地代码并安装优化测试包，没有更新 GitHub release。

## 已确认的原因

1. `PlaybackResolver` 只使用媒体的 base URL，忽略同轨道 backup URL。问题视频
   `BV1vHp96TErE` / CID `42680649431` 的首选地址为
   `*.edge.mountaintoys.cn:4483`。实际 FFmpeg 探针测得每次 Range 定位建立连接
   约 4.12～4.19 秒，媒体打开可达 8.15 秒；通用流信息探测仅约 0.09 秒。
2. 原 I/O 中断回调只检查 stop，新的定位不能取消旧的读取或尚未完成的定位。
   连续拖动会等待过期工作。
3. 音频时钟已定位而视频仍在获取/解码目标时，原 3 秒冻结检测会触发视频重建。
   1.58 实测中一次播放中定位触发该恢复，GUI 随后等待工作线程退出，进一步延迟。
4. 目标帧尚未被队列接收时，回调就可能标记 targetFrameReached；如果该帧被
   有界队列丢弃，暂停定位可能因此停止继续投喂。

## 最终修改

- 从同一个音视频轨道的服务端 URL 列表中选择地址：常规 HTTPS 首选保持原样；
  首选为 peer/非标准端口时，优先常规 HTTPS 备选。没有合适备选时保留原地址。
  同样支持 DASH 的 snake/camel case 字段和 progressive durl，未改写签名 URL、
  清晰度、编码选择、账号策略或直播解析。
- FFmpeg 读/定位操作携带定位序号，过期操作可协作取消；取消结果不当作 EOF，
  清理 AVIO 错误标志后在同一个解复用器/解码器上处理最新目标。
- 定位边界返回待显示及已完成 GPU 读取的旧 gralloc 槽位；共享 FBO 与前台、
  Cover、PiP 宿主保留。没有通过销毁播放器或重新加载媒体来实现定位。
- 正在定位的解码器获得最长 6 秒的有界宽限，避免当作正常播放冻结；目标已
  到达后原有 3 秒冻结恢复继续生效，并已通过注入真实冻结验证。
- 只在目标帧实际进入显示队列后标记就绪，且与定位序号更新串行；预解码中
  早于目标的帧直接返回槽位，避免无用的展示线程唤醒。
- 保留原来的 8 个压缩包额度、有界显示队列与 UHD 安全限制；通用
  `avformat_find_stream_info` 和音画启播屏障继续使用既有行为。
- 增加仅测试页可启用的独立性能记录，避免 journald 丢消息影响测量。
  `SILISILI_NATIVE_TEST_PERF_LOG` 只接受 `/tmp/silisili-perf-native-*.log`，不记录
  媒体 URL，普通启动不创建文件。测试页还可通过
  `SILISILI_NATIVE_TEST_PERF_PROFILE=baseline` 对比
  旧地址/I/O 路线；该参数不能改变普通启动。

## 测量结果

设备为 Pixel 3a XL / Sailfish OS 5.2.0.16 / aarch64，boot ID
`70375c04-f814-4707-8df6-711ee7a3deab`。问题视频始终为真实 1920×1080 AVC、
30 FPS，没有通过降低清晰度获得以下结果。

| 测量 | 1.58 问题记录 | 最终优化包实测 |
| --- | --- | --- |
| 问题视频播放请求至首帧 | 用户记录约 4.57 秒；冷启动复现 9.29 秒 | 1.28 秒 |
| 暂停定位至 90 秒目标帧 | 5.50 秒 | 1.62 秒 |
| 暂停返回 14 秒目标帧 | 6.31 秒 | 1.33 秒 |
| 播放中定位 120 秒 | 超过 10 秒，并触发重建 | 1.63 秒 |
| 播放中返回 30 秒 | 前项未完成 | 1.58 秒 |
| 连续 3 次拖动的最后目标 | 未完成该对照 | 0.35 秒 |

表中最终测量来自独立性能记录 `reliable-issue.log` 及 native log；定位的目标
PTS 独立于音频位置校验，GPU 纹理提交也单独记录。首帧测量从播放请求开始，
不包含此前的点击/页面动画时间，也不是物理屏幕扫描完成时间。

60 FPS 参考片源 `BV1P4ddBBEJF` 重复两次：启播 1.19～1.38 秒，四次定位
1.83～2.56 秒，快速连续拖动最后目标 0.20～0.23 秒。长 GOP 仍需预解码，
不能保证所有视频、所有网络均小于 2 秒。仅有 peer 地址或所有备选都慢时，
仍受节点和网络限制。

## 稳定性回归

- URL 选择的 Qt/C++ 实测单元检查：常规首选保持、同轨道不变、签名不改写、
  camel case、progressive、缺省字段、无备选回退及不降级 HTTPS。
- 两条片源的暂停/播放中前后定位、连续快速拖动、最后目标 PTS 正确；一个
  媒体加载、一个解码代际，无重建或软解回退。
- 完整 360P/480P/720P/1080P/1080P60 矩阵通过。矩阵测试完成后按设计主动
  stop，后续锁屏检查必须重新冷启动，不能把没有 MPRIS 服务当作产品故障。
- 1080P60 横屏连续 60 秒，同 PID 的 12 次五秒采样均持续前进；66 个约一秒
  呈现窗口最低 55.3907 FPS，低于 45 的窗口为 0。
- 锁屏物理播放/暂停、倍速、历史续播、强制软解、加载中暂停意图通过。
- 两次前后台往返、实时 Cover、系统 PiP 模式切换与拖动、正常退出后进程和
  MPRIS 服务消失、22/22 硬解缓冲引用平衡；应用内小窗拖动/关闭停止播放通过。
- 注入一次真实画面冻结后，原恢复检测正常重建视频 generation 1→2，仍只有
  一次媒体加载，音频未重载且共享纹理保留。
- 直播画面、暂停/继续、不可定位/速率 1 的能力声明通过。
- 多 P 从 CID `26635208162` 自动续播至 `27351058982`，同 PID 新首帧和
  MPRIS 当前分 P 一致。
- 源码清单、Node 检查、shell 语法及 `git diff --check` 通过。

早期尝试跳过完整 MP4 流探测、HTTP keep-alive 和扩大预解码窗口没有取得
足够的可验证收益，未保留在最终行为中。部分旧脚本曾因日志缺段或旧 Cover
坐标未完成，不算通过；最终以独立性能文件和重新定位卡片后的回归为准。
